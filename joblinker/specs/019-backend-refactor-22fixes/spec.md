## User Scenarios & Testing *(mandatory)*

### User Story 1 — System Compiles and Starts Cleanly (Priority: P1)

As a developer, I want the backend to compile without errors and start without missing dependencies, so that I can develop and deploy with confidence.

**Why this priority**: Compilation is a prerequisite for everything else. If the system doesn't compile, no other fix matters.

**Independent Test**: Run the build command and verify zero errors. Start the server and verify it connects to all external services (database, message queue, vector store).

**Acceptance Scenarios**:

1. **Given** the backend source code, **When** I run the build command, **Then** the build succeeds with zero errors
2. **Given** the server starts, **When** I check the health endpoint, **Then** it returns a healthy status
3. **Given** the server starts, **When** Chroma is reachable, **Then** the server initializes required collections and logs success

---

### User Story 2 — Data Extraction Returns Real Values (Priority: P1)

As a system operator, I want conversation data extraction functions to return actual extracted values (locations, skills, salaries) instead of placeholder strings, so that downstream features like preference storage and candidate matching produce meaningful results.

**Why this priority**: Placeholder strings ("extracted_from_conversation") pollute the preference store and make matching useless.

**Independent Test**: Feed sample conversation text into each extraction function and verify the output contains real extracted data, not placeholder strings.

**Acceptance Scenarios**:

1. **Given** a message containing "I'm looking for remote work in San Francisco", **When** the location extractor processes it, **Then** the result contains "remote" or "San Francisco"
2. **Given** a message mentioning "5 years of Go and Python experience", **When** the skills extractor processes it, **Then** the result contains "Go" and "Python"
3. **Given** a message stating "my target salary is $150,000", **When** the salary extractor processes it, **Then** the result contains "$150,000" or "150000"
4. **Given** a message with no extractable location, **When** the location extractor processes it, **Then** the result is a substring of the original content (not a hardcoded placeholder)

---

### User Story 3 — AI Agents Generate Real Responses (Priority: P1)

As a user interacting with the recruitment platform, I want AI agents to generate genuine, context-aware responses using the AI service, so that negotiations and conversations feel natural and productive.

**Why this priority**: Hardcoded template responses ("Seeker proposal in round N") break the illusion of intelligent agents and provide no real value.

**Independent Test**: Trigger a negotiation round and verify the response is generated by the AI service (not a template), contains context from the conversation, and varies between calls.

**Acceptance Scenarios**:

1. **Given** a negotiation with conversation history, **When** the seeker agent generates a proposal, **Then** the response references actual job or candidate details from the conversation
2. **Given** the reasoning service receives a user message, **When** it processes the message, **Then** it uses the AI service for intent classification (not just keyword matching)
3. **Given** the AI service is unavailable, **When** an agent tries to generate a response, **Then** a sensible fallback message is returned (not a template with round numbers)

---

### User Story 4 — No Hardcoded Business Values (Priority: P1)

As a platform operator, I want the system to derive salary figures, match scores, and other business values from actual data (job postings, candidate profiles, AI evaluations), so that the platform provides accurate and trustworthy information.

**Why this priority**: Hardcoded values (salary = 100000, target = 140000) mislead users and undermine trust in the platform.

**Independent Test**: Search the codebase for known hardcoded values and verify they are absent. Trigger fallback paths and verify responses contain no magic numbers.

**Acceptance Scenarios**:

1. **Given** the fallback response path is triggered for an INTEREST intent, **When** the response is generated, **Then** it contains no hardcoded salary numbers (100000, 140000, 110000)
2. **Given** a job offer creation where salary cannot be determined, **When** the system attempts to resolve salary, **Then** it derives from job data or returns an error (not a magic number)
3. **Given** any response from the system, **When** inspected, **Then** it contains no strings matching "extracted_from_conversation", "Seeker proposal in round", or "Based on my analysis:"

---

### User Story 5 — Database Schema Is Complete (Priority: P2)

As a developer, I want all required database tables to be automatically migrated on startup, so that no features fail at runtime due to missing tables.

**Why this priority**: Missing tables cause runtime panics that are hard to diagnose.

**Independent Test**: Start the server against a fresh database and verify all tables exist, including those for conversation summaries, agent memory, tool calls, and confirmation requests.

**Acceptance Scenarios**:

1. **Given** a fresh PostgreSQL database, **When** the server starts, **Then** tables for ConversationSummary, AgentToolCall, and ConfirmationRequest exist
2. **Given** the server has been running, **When** a new model is added, **Then** the next startup migrates the new table automatically

---

### User Story 6 — Integration Tests Are Trustworthy (Priority: P2)

As a developer, I want integration tests that actually test real behavior with real services, so that I can trust test results and catch regressions before deployment.

**Why this priority**: Tests with `t.Skip`, fake seed data, and hardcoded assertions provide false confidence.

**Independent Test**: Run the integration test suite against a running server and verify: no tests are skipped, all assertions check real values, and test data is generated at runtime.

**Acceptance Scenarios**:

1. **Given** the integration test suite, **When** run against a live server, **Then** no test calls `t.Skip` — missing dependencies cause `t.Fatal`
2. **Given** an integration test for authentication, **When** it registers a user, **Then** the email is randomly generated (not hardcoded)
3. **Given** an integration test for message handling, **When** it checks the response, **Then** it asserts the response does NOT contain known hardcoded strings

---

### User Story 7 — Dead Code Is Removed (Priority: P3)

As a developer, I want unused code removed from the codebase, so that the project is easier to understand and maintain.

**Why this priority**: Dead code creates confusion about which implementation is authoritative and increases the attack surface.

**Independent Test**: Verify specific dead files are removed and that the build still passes.

**Acceptance Scenarios**:

1. **Given** the old `internal/agent/memory.go` file, **When** the cleanup is complete, **Then** the file no longer exists and the build passes
2. **Given** the `GenerateEmbedding` function in the AI client, **When** the cleanup is complete, **Then** the function no longer exists (Chroma handles all embeddings)
3. **Given** the interview routes, **When** inspected, **Then** there is no route conflict between `/interviews/:id` and `/interviews/:matchId`

---

### Edge Cases

- What happens when the AI service is unreachable during a negotiation round? The system must fall back to a generic message, not crash or return a template with hardcoded values.
- What happens when Chroma is down on startup? The server should log a warning and continue, with collection initialization retried on first use.
- What happens when a salary cannot be extracted from any source? The system must return an error, not a magic number.
- What happens when two WebSocket connections join the same match? Both must receive messages for that match; neither must receive messages for other matches.

## Requirements *(mandatory)*

### Functional Requirements

**Phase 0 — Compilation**
- **FR-001**: System MUST compile without errors after all changes

**Phase 1 — Chroma Collections**
- **FR-002**: System MUST maintain a mapping from collection names to Chroma collection UUIDs
- **FR-003**: System MUST create collections on startup if they don't exist ("agent_memories", "user_preferences")
- **FR-004**: All Chroma operations (Add, Query, Delete, Get) MUST resolve collection names to UUIDs internally

**Phase 2 — Data Extraction**
- **FR-005**: Location extractor MUST detect keywords: remote, onsite, hybrid, and common city names
- **FR-006**: Skills extractor MUST match a predefined list of common technical skills
- **FR-007**: Salary extractor MUST NOT return the placeholder string "extracted_from_conversation"
- **FR-008**: All extractors MUST return a substring of the original content as fallback (not a hardcoded placeholder)

**Phase 3 — AI Integration**
- **FR-009**: `generateSeekerProposal` MUST call the AI service to generate proposals
- **FR-010**: `understandPhase` MUST use AI for intent classification when available
- **FR-011**: `respondPhase` MUST use AI for response generation when available
- **FR-012**: All AI-calling functions MUST have graceful fallbacks when the AI service is unavailable

**Phase 4 — Hardcoded Values**
- **FR-013**: `fallbackResponse` MUST NOT contain hardcoded salary numbers (100000, 140000, 110000)
- **FR-014**: Offer salary resolution MUST derive values from job data or return an error
- **FR-015**: No response from the system MUST contain known hardcoded strings

**Phase 5 — Database Schema**
- **FR-016**: AutoMigrate MUST include models: AgentMemory, ConversationSummary, AgentToolCall, ConfirmationRequest

**Phase 6 — Testing**
- **FR-017**: Integration tests MUST NOT use `t.Skip` — missing dependencies cause `t.Fatal`
- **FR-018**: Integration tests MUST generate all test data at runtime (random emails, UUIDs)
- **FR-019**: Integration tests MUST include anti-hardcoded assertions (checking response does NOT contain known fake values)
- **FR-020**: Test infrastructure MUST provide helper functions for common operations (register, create agent, create job)

**Phase 7 — Dead Code**
- **FR-021**: `internal/agent/memory.go` MUST be deleted
- **FR-022**: `GenerateEmbedding` in the AI client MUST be deleted
- **FR-023**: API key length MUST NOT be logged
- **FR-024**: Protobuf frame timestamp MUST use `time.Now().UnixMilli()` (not 0)
- **FR-025**: Interview routes MUST NOT conflict (resolve `:id` vs `:matchId` ambiguity)

### Key Entities

- **ChromaCollection**: Represents a named vector collection with a UUID. Key attributes: name, UUID, created_at.
- **ExtractedPreference**: Represents a preference extracted from conversation. Key attributes: type (salary/location/skills/job_type), value, confidence.
- **ConfirmationRequest**: Represents a pending human confirmation for an AI-negotiated agreement. Key attributes: match_id, terms, status.
